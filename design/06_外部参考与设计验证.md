## 2. BTC 周期分析类项目对比

| 项目 | 做了什么 | 我们的差异 |
|------|----------|-----------|
| [giocaizzi/btc-cycles](https://github.com/giocaizzi/btc-cycles) | 减半周期叠加可视化 | 我们有退火缩放，他们只做原始叠加 |
| [FranciscoBuru/BTC-Halving](https://github.com/FranciscoBuru/BTC-Halving) | 基于历史周期预测峰值时间窗口 | 我们有三模型融合，他们只用单一方法 |
| [nafisalawalidris/Bitcoin-Price-Analysis](https://github.com/nafisalawalidris/Bitcoin-Price-Analysis-Before-the-2024-Halving) | ML 预测价格趋势 | 我们不用 ML，强调可解释性 |
| [jofpin/synthBTC](https://github.com/jofpin/synthBTC) | 蒙特卡洛模拟概率分布 | 有趣，可作为未来扩展（概率区间输出） |
| [yohplala/halvix](https://github.com/yohplala/halvix) | 周期叠加图 | 类似但更简单 |

### 结论

**我们的波动退火 + 多模型融合在开源 BTC 分析中是独特的。** 大多数项目只做原始周期叠加，没有考虑跨周期波动递减。

## 3. 投资决策系统对比

### 3.1 Ghostfolio (开源个人投资管理)

```
Ghostfolio 架构:
  Angular + NestJS + Prisma + PostgreSQL

  数据流:
    Orders/Accounts → PortfolioService → PortfolioCalculator
                                       → Performance Metrics
                                       → Risk Assessment (按市场/资产类别)
```

**可借鉴的点：**
- 风险评估按维度拆分（市场、行业、资产类别）→ 类似我们的三层架构
- 数据采集、计算、展示三层分离 → 验证了我们 L0→L4 的数据层级设计

**不适用的点：**
- Ghostfolio 是资产净值中心，我们明确**不做**净值跟踪
- 我们的核心是"要不要做"的决策，不是"做了之后的管理"

### 3.2 Quantropy (模块化量化分析框架)

```
Quantropy 流水线:
  Data Ingestion → Risk Factor Modeling → Stock Screening
                                       → Portfolio Optimization
                                       → Broker API
```

**可借鉴的点：**
- 模块化设计，每个模块可独立使用 → 与我们的插件理念一致
- OOP + 函数式编程混合 → 适合核心算法（函数式）+ 插件管理（OOP）

### 3.3 FinanceToolkit (150+ 金融指标库)

**可借鉴的点：**
- "每个计算用最简单的方式写出来" → 对我们的**算法规格书**有直接启发
- 指标作为可组合的透明函数，而不是黑盒 → 验证了我们 score 插件的设计

## 4. 插件架构对比：OpenBB vs 我们

### OpenBB Platform 的插件系统

```
OpenBB 架构:
  openbb-core (核心) + Extensions (扩展)

  Extensions 分两类:
    Provider Extensions: 数据源 (ETL 模式)
    Toolkit Extensions: 分析工具

  发现机制: Python entry_points (pyproject.toml)
  API 层: FastAPI + Pydantic 校验
  Router: 核心路由层, 定义 100+ 端点
```

### 对比

| 维度 | OpenBB | 我们的设计 |
|------|--------|-----------|
| 插件发现 | Python entry_points 自动扫描 | manifest.yaml + 目录扫描 |
| 数据获取 | ETL 模式 (Extract→Transform→Load) | 类似，但更简单 (Fetch→Clean→Store) |
| API 框架 | FastAPI + Pydantic | FastAPI + Pydantic (一致) |
| 输出标准化 | Pydantic models + 统一 schema | PluginOutput dataclass |
| 插件粒度 | 每个数据源/工具一个包 | 每个标的一个目录 |

### 我们可以借鉴的

1. **用 Pydantic 替代 dataclass 做 PluginOutput**
   - 自动校验字段类型和范围
   - 自动生成 JSON Schema → 前端可直接用
   - 与 FastAPI 天然集成

2. **插件注册用 entry_points 而非目录扫描**
   - 但对于个人项目，目录扫描 + manifest.yaml 已经足够简单
   - entry_points 适合分布式开发（多人多包），我们暂不需要

3. **ETL 模式标准化数据获取**
   - 每个数据源实现 `extract()`, `transform()`, `load()` 三个方法
   - 对我们的 data_loader.py 有参考价值

## 5. 多因子评分系统对比

### Multi-Factor-Stock-Ranking-Engine

```
6 因子: Value, Size, Momentum, Low Volatility, Quality, Market Risk
用户自定义权重 → 加权复合评分 → 排名

输出: 排名列表 + 每个因子分数 + 加权总分
```

### 与我们 score 插件的对比

| 维度 | 多因子排名引擎 | 我们的 score 系统 |
|------|---------------|-----------------|
| 目标 | 选出最好的股票 | 判断一个机会是否适合我 |
| 因子 | 6 个标准因子 | 可插拔 score 插件 |
| 权重 | 用户自定义 | policy.yaml 配置 |
| 输出 | 排名 + 总分 | 信号 + 风险等级 + 置信度 |
| 关键差异 | **相对排名**（谁比谁好） | **绝对判断**（这个值不值得做） |

### 关键洞察

**我们的系统不是排名系统，是决策系统。**

排名系统回答"这 100 只股票哪个最好"。
我们回答"这一个机会，对现在的我，值不值得做"。

这意味着：
- 我们**不需要**在标的之间做排名
- 我们**需要**每个标的有独立的"值不值得做"判断
- 三层交叉判定矩阵是我们的独特设计，在开源项目中几乎没有对标

## 6. 量化交易系统架构对比

### 业界共识的五层架构

```
① Data Layer       → 数据采集 + 校验 + 存储
② Signal Layer     → 把数据转化为信号
③ Portfolio Layer  → 结合约束条件构建组合
④ Execution Layer  → 执行交易
⑤ Analytics Layer  → 回测 + 归因 + 反馈
```

### 与我们的映射

```
业界五层               我们的三层 + 决策中心

① Data Layer      →  L0/L1 (04_数据流 §3)
② Signal Layer    →  机会层插件 (01_插件规范)
③ Portfolio Layer  →  ≈ 决策中心的交叉判定 (00 §5)
                      + 个人层约束 (02 §6)
④ Execution Layer →  不做 (明确不做交易执行)
⑤ Analytics Layer →  决策中心的"复盘记录" (00 §5)
```

### 关键差异

| 维度 | 量化交易系统 | 我们 |
|------|------------|------|
| 目标 | 自动化交易盈利 | 辅助决策判断 |
| 执行 | 自动下单 | 不做执行，给建议 |
| 频率 | 高频/日频 | 日频/周频 |
| 用户 | 量化研究员 | 普通个人投资者 |
| 复杂度 | 极高 | 中等，可解释性优先 |

**我们在第③层做了创新：把"个人约束"作为 portfolio construction 的替代。**

量化系统的约束是风险模型（VaR, 相关性矩阵等）。
我们的约束是"我的现金流扛不扛得住"。

## 7. 微软 Qlib 的设计哲学

```
Qlib 核心原则:
  1. 完全模块化, 松耦合
  2. 每个模块可独立使用
  3. 提供 "能用的默认实现" + "可替换的接口"
  4. 研究者可以只替换一个模块, 不动其他
```

### 对我们的启发

**"Default implementations with override"** 模式：

```python
# 我们可以这样做:

class BTCCyclePlugin(OpportunityPlugin):
    """默认的 BTC 周期分析插件。直接能用。"""

    def run(self) -> PluginOutput:
        # 默认实现: 完整的退火 + 融合 + 信号
        ...

class BTCCyclePluginV2(BTCCyclePlugin):
    """改进版: 只覆盖 signal_judge, 其他复用。"""

    def _judge(self, ...):
        # 新的判定规则
        ...
```

这意味着：
- 未来调整判定规则时，不需要重写整个插件
- 只需要继承 + 覆盖特定方法
- 旧版本仍然可用（做对比）

## 8. 确定性评分 vs ML 分类

### 业界讨论

来自 Signal Scoring Pipeline 设计模式的核心观点：

> **Deterministic scoring (确定性评分) 优于 ML classification (ML 分类) 用于决策支持。**
>
> 原因：用户需要理解"为什么这个分数是这个值"。

### 对我们的验证

**我们的设计选择是正确的：**

- 不用 ML 做信号判定 ✓
- 每个 score 有明确的计算公式和 reasoning ✓
- policy 权重可配置、可解释 ✓
- 置信度由明确的 4 因子公式计算（05 §7），不是 ML 输出的概率 ✓

如果未来想加 ML：
- 可以作为**一个 score 插件**接入，而不是替代整个判定逻辑
- 例如 `ml_sentiment_score` 插件，输出格式与其他 score 一致
- policy 层决定它的权重（可以很低）
