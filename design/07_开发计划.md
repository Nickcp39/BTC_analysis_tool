## 2. 开发方法论

### 2.1 为什么不用标准 Scrum/Agile

标准 Agile 假设有团队、有 Sprint Review、有 Stakeholder Feedback Loop。

1 人项目更适合：

**Modified Solo Kanban + Milestone-Driven Development**

- 不设固定 Sprint，按 Milestone 推进
- 每个 Milestone 有明确的 Done Criteria
- 用 "能跑就发" 原则：每个 Milestone 结束时系统必须是可运行的
- 不做提前优化，不做提前抽象，只在真正需要时重构

### 2.2 Personal Kanban 看板

不用复杂的项目管理工具。用三列看板：

```
┌──────────────┬──────────────┬──────────────┐
│   Now (≤3)   │    Next      │    Later     │
│   正在做      │   下一步      │   以后再说    │
├──────────────┼──────────────┼──────────────┤
│              │              │              │
│  [当前任务1]  │  [排队任务]   │  [粗粒度想法] │
│  [当前任务2]  │  [排队任务]   │              │
│              │              │              │
│  WIP 限制: 3 │  详细到任务级  │  只写一句话   │
│              │  (< 4小时)    │              │
└──────────────┴──────────────┴──────────────┘
```

**核心规则：**
- Now 列最多 3 项（WIP 限制）— 避免上下文切换
- 只详细规划未来 2 周的任务，更远的保持粗粒度
- 完成一项才拉入一项
- 每天问自己：**"今天能 ship 什么？"**

### 2.3 核心原则

参考 OpenBB、Qlib 等成功开源项目的经验（详见 [06_外部参考](./06_外部参考与设计验证.md)）：

| 原则 | 做法 | 来源 |
|------|------|------|
| **Vertical Slice** | 每个 M 交付完整纵切面（数据→API→展示） | Qlib 模块独立原则 |
| **Working > Perfect** | M1 可以丑但能用，M2 再优化 | Solo dev 共识 |
| **Test as You Go** | 写完立刻测试，不攒到最后 | FastAPI best practices |
| **配置 > 硬编码** | 参数从一开始放 config | OpenBB ETL 模式 |
| **数值一致性是红线** | 工程化结果必须与原脚本完全一致 | 本项目特殊要求 |
| **每个任务 < 4h** | 超过 4h 的任务要再拆分 | Hofstadter's Law |
| **Daily shipping** | 每天至少 commit 一次有意义的进展 | 动量 > 完美 |

### 2.4 时间估算方法

基于 1 人、业余时间的现实估算：

```
每周可投入时间: ~10-15 小时（含周末）
每个开发日: ~2-3 小时有效编码时间
缓冲系数: ×1.5（意外问题、调试、返工）

估算公式:
  乐观时间 × 1.5 = 计划时间
  计划时间 × 1.3 = 保守时间
```

### 2.5 时间跟踪

**前 2 周记录实际时间 vs 估算时间，算出个人乘数。**

```
示例:
  任务: "实现退火缩放模块"
  估算: 4h
  实际: 5.5h
  个人乘数: 5.5/4 = 1.375

前2周平均乘数: 1.4 → 后续所有估算 × 1.4
```

### 7.2 Snapshot 机制

```
每日定时任务 (08:00):
  1. 拉取 FRED 最新数据
  2. 校验数据完整性
  3. 运行完整 pipeline
  4. 生成新 snapshot (JSON)
  5. 校验通过 → 切换为 active
  6. 校验失败 → 保留旧 active，记录错误日志

用户请求时:
  1. 读取 active snapshot
  2. 直接返回 (不重算)
  3. 如果 snapshot 过期(>24h) → 后台触发更新，先返回旧结果
```

## 11. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 数值不一致（工程化后结果不同） | 中 | **高** | M1 阶段投入足够的一致性测试时间 |
| FRED API 变动或限流 | 低 | 中 | 增加备用数据源（Yahoo Finance） |
| 时间投入不稳定 | 高 | 中 | M0-M2 是核心，M3-M4 可延后 |
| 过度设计（想太多不动手） | 中 | 高 | 每个 M 必须有 working code |
| 前端投入过多 | 中 | 中 | V1 用纯 HTML + ECharts，不上框架 |

### 11.1 减速策略

如果时间紧张，优先级：

```
必须做: M0 → M1 → M2 (核心价值)
应该做: M3 (扩展性)
可以晚做: M4 (完整性)
可以不做: 微信小程序 (用网页替代)
```

## 15. 决策日志

开发过程中的重要技术决策记录在这里，避免反复讨论已决定的事。

| 日期 | 决策 | 理由 | 替代方案（为什么不选） |
|------|------|------|----------------------|
| 2026-03-19 | 用 FastAPI 而不是 Flask/Django | 异步、自动文档、Pydantic 原生集成 | Flask 太轻缺乏类型校验; Django 太重 |
| 2026-03-19 | 用 SQLite 而不是 PostgreSQL | 单机部署、零运维、足够 | PostgreSQL 对 1 人项目过重 |
| 2026-03-19 | 前端 V1 用纯 HTML+ECharts 而非 React/Vue | 最小依赖、直接部署、个人用足够 | SPA 框架增加复杂度无实际收益 |
| 2026-03-19 | 用 Pydantic 替代 dataclass | 自动校验 + JSON Schema + FastAPI 集成 | dataclass 缺乏运行时校验 |
| 2026-03-19 | 不用 ML 做信号判定 | 可解释性优先，确定性评分 | ML 黑盒不适合个人决策工具 |
| 2026-03-19 | M0-M2 为核心路径，M3-M4 可延 | MVU 在 M2，先实现个人可用 | 先做完再发布会拖太久 |
